## Goal

Build a personal finance tracking system for a user who manages multiple credit cards and savings (debit) accounts at a Peruvian bank. The system must:

- Import bank Excel files (Fecha / Descripcion / Moneda / Monto columns; debit adds N° Operacion)
- Detect duplicate transactions across overlapping Excel downloads
- Auto-categorize transactions via configurable rules
- Manage recurrent transactions (known monthly/yearly charges) with manual or automatic matching
- Perform credit-card-only cycle conciliation to detect interest charges
- Track transfers between debit accounts and payments from debit to credit card
- Store everything in localStorage first (fast UI iteration), then migrate to the Java backend

### What changed in this session (DESIGN_LOCAL v1.1 → v1.2)

#### ExcelParserService — Column name constants

The six Excel column header strings (`Fecha`, `Descripcion`, `Moneda`, `Monto`, `N° Operacion`, `Operacion`) are now declared as named constants at the top of the service file. Previously they were inline string literals scattered through `.filter()` and `.map()` calls. Changing the constant is now a single-line edit if the bank ever changes its export format.

#### RawImportRow — Moved to models, English field names, amountPen added

`RawImportRow` was defined as an inline `export interface` inside `excel-parser.service.ts`. It is now declared in `src/app/core/models/import-batch.model.ts` alongside the other domain interfaces.

Field name changes (Spanish → English):

| Old field | New field | Type |
|---|---|---|
| `fecha` | `dateTransaction` | `string` (YYYY-MM-DD) |
| `descripcion` | `description` | `string` |
| `moneda` | `currency` | `'PEN' \| 'USD'` |
| `monto` | `amount` | `number` |
| *(new)* | `amountPen` | `number` |

`amountPen` is computed at parse time inside `ExcelParserService.parseFile(file, usdExchangeRate)`. The exchange rate is now a required parameter of `parseFile`. This eliminates the `decAmountPen` computation that previously happened in `StepUploadComponent`'s "On Next" handler — the row arrives from the parser already fully resolved.

All downstream references updated: `DuplicationLogicService` (field accesses in all six rules), `AnnotatedImportRow.raw` (TypeScript structural typing ensures compile-time coverage), and the transaction-mapping code in the import wizard Step 3.

#### Import Wizard — Promoted to 3 steps

The wizard previously had two steps: **Upload** → **Review (with Confirm)**. It now has three:

| Step | Component | When data is written |
|---|---|---|
| 1 — Upload | `StepUploadComponent` | Never (state only) |
| 2 — Review | `StepReviewComponent` | Soft-deletes only (user clicks trash icon) |
| 3 — Finalize | `StepFinalizeComponent` (new) | All import writes happen here |

Step 2's "Confirm" button is replaced by "Next →". All localStorage writes were moved from Step 2 to Step 3 in the following order:

1. Create `ImportBatch`
2. Save checked `Transaction` records via `TransactionService.saveMany()`
3. Update `account.decCurrentBalance`
4. Run `RecurrentMatchingService.findAutomaticMatches()` against all now-active transactions and auto-save any new `RecurrentTransactionMatch` records found
5. Check storage size (warn if > 4 MB)
6. Reset `ImportWizardState`
7. Navigate to the **conciliation page** (`ROUTES.CONCILIATION`)

Step 3 also displays a read-only summary (account name, transaction count, auto-duplicates skipped, exchange rate) before the user commits.

## Key Design Decisions (do not re-litigate)

| Decision | Detail |
|---|---|
| Amounts | Negative = charge/spend; positive = payment/refund. Bank statement convention. |
| USD conversion | Fixed at parse time inside `ExcelParserService.parseFile(file, usdExchangeRate)`. `amountPen` is computed once and stored. Never re-converted. |
| Account model | `Transaction.accountId` + `accountType` (CREDIT_CARD or DEBIT_ACCOUNT). No separate tables. |
| Dupe detection | 6 rules: D1 (debit op#), A1 (exact), A2 (USD ±3d), P1 (prefix+amount+date), P2 (amount+date), P3 (collection). First match wins. |
| Category matching | Priority-ordered rules (intPriority ASC). First match wins. 4 match types. |
| Conciliation | Credit cards only. amountA = openingBalance + cycleMovements; amountB = currentBalance − postCloseMovements; interest = amountB − amountA. |
| Recurrent iterations | MONTHLY key = 'YYYY-MM', YEARLY key = 'YYYY'. One match per iteration, stop after first. |
| Transfers | Two transactions with shared `transferGroupId`. Source: negative; destination: positive. |
| PENDING status | Manually declarable. Also settable during import wizard Step 2 context menu. Included in balance estimates. |
| Balance field | `decCurrentBalance` on both CreditCard and DebitAccount; updated after every import (Step 3) and (for credit) conciliation. |
| Import wizard writes | All writes deferred to Step 3 — no partial state in localStorage if the user abandons mid-wizard. |
| Post-import navigation | Step 3 always navigates to `ROUTES.CONCILIATION` on completion. |
